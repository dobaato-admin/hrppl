## 3. What was built this session

Six commits on `main`, in order. Each has a long commit message with the
reasoning; `git log --format=%B 5f35dd6..HEAD` is worth reading.

### `fix/hook-error-exposure` — the CodeQL finding
GitHub flagged "Information exposure through a stack trace" on
`leave-accrual.ts`. It was systematic: **15 of 20** `/api/public/hooks/*`
handlers echoed `e.message` into the response body. Those endpoints authenticate
with a bearer secret, not a session, so the body is internet-reachable, and the
errors are Postgres/PostgREST messages naming tables, columns, constraints and
RLS policies.

`src/lib/hook-response.server.ts` — `hookFailure()` logs the full error and
returns a generic message plus a correlation ref; `hookErrorRef()` does the same
inside per-item arrays. Two deliberate exceptions, both documented in the file:
Zod issues still return on a 400 (they describe the caller's own payload), and
`billing_admin_alerts` still stores `e.message` (internal table).

`tests/hook-error-exposure.test.ts` guards it, and **resolves variables**, not
just the literal `.message` shape — the flagged file built the message two lines
above the response and passed the variable in, so a shape-only scan called it
clean. Five fixtures pin the cases the detector must catch.

### `feat/clock-in-widget` — attendance correctness
Three real bugs, all of which changed recorded pay:

1. **`work_date` was computed in UTC.** `new Date().toISOString().slice(0,10)`
   is today *in UTC*. In `Asia/Kathmandu` (+05:45) an early shift filed against
   yesterday; in `America/New_York` an evening shift filed against tomorrow. The
   visible symptom came from the week grid, which built each column from a local
   midnight `Date` and ran it through the same conversion, so every column
   queried the day before its own label. Fixed by `src/lib/work-date.ts`.
2. **The timestamp was taken at response time.** The server stamped
   `new Date()` inside the handler — after auth, the employee lookup, the
   geofence query, and up to 8s waiting on geolocation. Every punch was late,
   always in the employer's favour. The client now sends `clientTime`;
   `resolvePunchInstant` believes it within ±5 min, otherwise substitutes server
   time and records `clock_in_skew_seconds`.
3. **GPS accuracy was discarded**, as was `sign_geofences.min_accuracy_meters`,
   which nothing had ever read. `src/lib/geofence.ts` `evaluateGeofence` returns
   `inside` / `inside_low_confidence` / `uncertain` / `outside`, generous at the
   boundary on purpose: a false refusal stops someone working and is visible
   instantly; a false acceptance is recorded and reviewable.

Plus the floating `ClockWidget` (renders once inside `ShellInner`, hides itself
for accounts with no employee row), WFH as the sanctioned geofence exception,
and refusals now written to `geofence_audit_log` through the service-role client
inside `try/catch`.

### `chore/apply-attendance-migration`
Applied `20260823060000`, regenerated `types.ts` via a new
`scripts/apply-migration.mjs --types`, and deleted all 46 `PendingSchema` casts.

Removing them exposed a bug they had hidden: `listWfhForApproval` built its
`.select()` with string concatenation, and **TypeScript types `"a" + "b"` as
plain `string`, not `"ab"`**. supabase-js parses that argument at the type level,
so the embed degraded to `GenericStringError` and every field was silently
untyped. Always pass one string literal to `.select()`.

### `feat/requests-inbox-and-clock-ux`
Clock-in latency was **geolocation, not the server**: a cold
`getCurrentPosition` with `enableHighAccuracy` takes most of 8s on a laptop.
Position is now pre-warmed on panel open and on hover, reused for 90s, and an
approved-WFH day drops to a 2.5s low-accuracy attempt because the fence will be
bypassed anyway.

Toasts moved to **top-right** — sonner defaults to bottom-right, exactly where
the widget sits, so every confirmation covered the control you next wanted.

`getClockStatus` now returns the tenant's fences, so the widget runs the same
`evaluateGeofence` the server will and shows status *before* the punch.

See §4.

## 4. The WFH lifecycle, and the trap that made it fake

The user reported three things. Testing them against the live database confirmed
one, explained the second, and turned up a fourth that was worse than all three.

| Report | Finding |
| --- | --- |
| Managers can self-apply *and* self-approve? | **Real hole.** The server fn refused it; nothing else did. The approver policy was `FOR ALL` across the tenant with no self-exclusion, so a manager could PATCH their own row through PostgREST. |
| Manager with approved WFH can't clock in | The gate was fine. Self-decision was blocked in the fn *and* the row hidden from their own queue, so a manager's request had **no route to approval at all** — it sat pending forever. |
| Approved request can still be withdrawn | Didn't reproduce for a plain employee. Reproduced for approvers, via the same hole. |

### The trap: `SECURITY DEFINER` hides the caller

The lifecycle trigger's escape hatch for trusted server paths was wrong twice:

- `session_user` — the *connection's* role. Does not follow `SET ROLE`, so it
  never matched via PostgREST's pooled connection, and always matched anything
  connected directly as `postgres`.
- `current_user` — correct in ordinary code. But the trigger is
  `SECURITY DEFINER`, where **`current_user` is the function owner**. It matched
  on every call from every caller and the entire state machine was dead code.

Neither identifies the caller inside `SECURITY DEFINER`. Only the request context
does:

```sql
jwt_role := auth.role();
IF jwt_role IS NULL              -- migration, seed, psql: no JWT at all
   OR jwt_role = 'service_role'  -- the backend acting deliberately
THEN RETURN NEW; END IF;         -- everything else is a person: enforce
```

This is also what makes the rules testable. **Verify RLS and triggers under a
real JWT, never as `postgres`** — `apply-migration.mjs --sql` runs as `postgres`
and will happily tell you a broken policy works.

### The rules now in Postgres (`tg_wfh_lifecycle` + RLS)

```
pending  → approved / rejected   an approver who is NOT the requester
pending  → cancelled             the requester (or an approver)
approved → cancelled             requester before the window opens;
                                 approver at any time
anything else                    refused
```

Plus: must start `pending`; cannot be wholly in the past; cannot overlap another
pending/approved window for the same employee; dates and owner freeze once
decided; and **an approval cannot be revoked once a remote punch exists under
it** — that punch was made in good faith and attendance is the input to pay.

A manager may raise a request and may never decide it, whatever roles they hold.
That is why `/admin/requests` shows their own row (a repository must be complete)
while the actionable queue hides it (you cannot act on it).

### The requests inbox

Six tables model "somebody asked, somebody decides".
`src/lib/requests-inbox.functions.ts` normalises all six — including six
different status vocabularies — into one `InboxRow`. An unknown status groups as
`pending` rather than being dropped.

- `/me/requests` — personal only.
- `/admin/requests` — the organisation-wide repository, all types, all states,
  filters, search, history. Ticket decisions inline; everything else deep-links.
- Both render through `src/components/requests/RequestList.tsx`.

`tests/requests-links.test.ts` pins every deep link against
**`FileRoutesByFullPath`** — *not* the `path:` literals, which are relative to
the parent and report every nested route as dead. It caught `/admin/support`,
a route that has never existed.

## 5. Verification runbook

The SQL harnesses live in the session scratchpad, which **does not travel**.
Recreate them from `CLAUDE.md` when needed; the shape is:

```sql
SELECT set_config('request.jwt.claims',
  json_build_object('sub', '<user-uuid>', 'role', 'authenticated')::text, true);
SET LOCAL ROLE authenticated;
SELECT count(*) FROM your_table;   -- then RESET ROLE
```

Two things that cost time and are worth knowing:

- `apply-migration.mjs` prints only the **final result set, truncated to 500
  chars**, and swallows `RAISE NOTICE`. Collect findings into a temp table and
  `string_agg` them into one short row.
- Make fixtures **self-contained**. An early harness consumed the seeded
  approved WFH row and left the demo without one; a later run then reported
  "no rows" that looked like a bug. Demo WFH data was reset to: `ella` and
  `nina` approved (today → +2), `evan` and `raj` pending (+5).

(`leave.functions.ts:77`) with no balance check and no weekend/holiday

## 7. Tooling notes

- `scripts/qa-sweep.mjs` walks every nav destination as each seeded role and
  writes `docs/qa-sweep-report.md`. Re-run after structural changes. It waits on
  the sidebar selector rather than sleeping — a flat sleep is wrong in both
  directions and once produced 102 false "no chrome" findings.
- `node scripts/apply-migration.mjs <file.sql>` then **always** `--types`.
  202 migrations; the endpoint is not transactional across statements, which is
  why every migration uses `IF NOT EXISTS` / `DROP POLICY IF EXISTS` guards —
  re-running is the recovery.
- The Supabase **MCP server is unauthenticated** in this environment. It needs
  authorising via `claude mcp` or `/mcp` in an interactive session; until then
  its tools are unavailable. Nothing above depends on it —
  `scripts/apply-migration.mjs` covers the same ground through the Management
  API.
